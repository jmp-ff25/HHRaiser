# Ревью читаемости HHRaiser

## Порядок проверки

1. Прочитать `git diff` и назвать цель изменения.
2. Проверить только изменённые строки и ближайший вызывающий контекст.
3. Отделить блокирующие проблемы от необязательных улучшений.
4. Не требовать абстракций, классов или констант ради формальности.

## Чек-лист

- У каждой функции одна понятная ответственность; длинная функция разбита по
  смысловым фазам или небольшим именованным шагам.
- Нет импорта приватного имени из другого модуля и нет новой циклической зависимости.
- Имена отражают бизнес-смысл, а не техническую случайность.
- Отступы отделяют логические части, но не превращают код в разреженный текст.
- Магические значения вынесены только когда выражают правило, ограничение,
  таймаут или повторяются.
- Комментарии и docstring-и на русском; они объясняют зачем, ограничения HH,
  Playwright или SQLite, а не очевидный синтаксис.
- Не изменены гарантии безопасности: CAPTCHA, неизвестный исход отклика,
  закрытие браузера, секреты и миграции.
- Для каждого изменённого поведения есть проверка; для чистого рефакторинга
  существующие тесты остаются зелёными.

## Формат результата

Писать только конкретные замечания:

- `блокирующее — файл:строка — причина и минимальное исправление`;
- `важное — файл:строка — причина`;
- `идея — файл:строка — необязательное улучшение`.

Если замечаний нет, прямо написать: `Замечаний, блокирующих коммит, нет.`
