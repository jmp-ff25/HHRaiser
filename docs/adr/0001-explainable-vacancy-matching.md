# ADR-0001: объяснимое сопоставление вакансии с резюме

- Статус: принято
- Дата: 2026-09-10

## Контекст

До этого решения HHRaiser содержательно просматривал любую ещё не посещённую
вакансию из настроенной выдачи. Владельцу нужен предварительный локальный фильтр,
который использует выбранное резюме, работает на слабом CPU и объясняет числовой
результат. Текст резюме и вакансий не должен отправляться внешнему сервису или
сохраняться в аналитической базе.

Значение должно быть пригодно для будущего сценария принятия решения перед
откликом. На момент принятия решения проект не отправлял отклики; позднее безопасный
опциональный сценарий добавлен в [ADR-0004](0004-safe-vacancy-responses.md).

## Решение

Использовать детерминированный ансамбль классических методов без генеративной LLM:

1. Нормализовать регистр, `ё/е`, пробелы и выделить значимые русские и латинские
   токены.
2. Рассчитать коэффициент Дайса между названием выбранного резюме и названием
   вакансии.
3. Рассчитать нормированное BM25F-подобное покрытие терминов. Название вакансии
   имеет вес 3, семантические теги навыков HH — 4, описание — 1. Для терминов
   используется положительная сглаженная IDF и насыщение частоты BM25 с `k1=1.2`.
4. Рассчитать покрытие явно указанных навыков: долю тегов вакансии, найденных в
   тексте резюме как нормализованная фраза или полный набор токенов.
5. Рассчитать косинусную близость частотных векторов терминов описания и резюме.
6. Объединить признаки логистической функцией:

   ```text
   z = -2.2
       + 1.8 * title_similarity
       + 2.2 * bm25f_relevance
       + 1.8 * skills_coverage
       + 0.8 * lexical_similarity

   score = round(100 / (1 + exp(-z)))
   ```

7. Просматривать вакансию только при `score >= threshold`. Порог по умолчанию —
   55 и настраивается в `[matching]` или через CLI.

Это значение называется **расчётной оценкой совместимости**, а не доказанной
вероятностью. Коэффициенты заданы как стартовая инженерная политика. После появления
явных пользовательских меток `подходит/не подходит` они должны быть обучены
логистической регрессией и откалиброваны на отдельной выборке методом Платта или
изотонической регрессией. Только после проверки calibration curve результат можно
называть эмпирической вероятностью.

## Порядок браузерного действия

1. Открыть канонический URL вакансии и дождаться DOM.
2. Прочитать заголовок, описание и семантические теги навыков без прокрутки.
3. Рассчитать оценку.
4. Если порог не пройден, не прокручивать страницу и не ждать время просмотра.
5. Если порог пройден, выполнить обычную прокрутку и содержательный просмотр.
6. Сохранить в SQLite только публичный ID, оценку, решение и время. Полный текст,
   URL с параметрами и содержимое резюме не сохранять.

Нераспознанный текст резюме приводит к fail-open: вакансия просматривается по
прежнему сценарию, а лог явно сообщает, что фильтр не применён. Неполное состояние
страницы остаётся `unknown outcome` и может быть проверено позднее.

## Рассмотренные альтернативы

### Генеративная локальная LLM

Отклонена для первой версии из-за расхода RAM, низкой скорости на VPS с двумя
ядрами, нестабильности числовой оценки и сложности воспроизводимого объяснения.

### Только TF-IDF или BM25

Отклонено как единственный критерий: текстовая релевантность не различает важность
названия, навыков и общего описания. Компоненты информационного поиска сохранены как
часть ансамбля.

### Небольшая embedding-модель

Отложена. Она полезна для неявных синонимов, но добавляет модель и runtime. В
будущем её косинусную близость можно добавить новым признаком, не меняя контракт
решения.

## Последствия

Положительные:

- одинаковый ввод даёт одинаковый результат;
- алгоритм работает на Windows и малом Ubuntu VPS без GPU;
- каждый вклад в оценку наблюдаем и тестируется отдельно;
- приватный текст остаётся только в памяти процесса;
- отфильтрованные вакансии не считаются просмотренными, но не выбираются повторно
  в текущем цикле уникальности.

Ограничения:

- точность зависит от качества текста и тегов HH;
- синонимы без общих токенов могут быть пропущены;
- стартовые коэффициенты не персонализированы;
- оценка до накопления и калибровки пользовательских меток не является статистически
  подтверждённой вероятностью.
