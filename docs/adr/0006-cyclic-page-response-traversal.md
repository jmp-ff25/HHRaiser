# ADR-0006: циклический обход страниц и журнал терминальных откликов

- Статус: принято
- Дата: 2026-09-15

## Контекст

Отбор по истории просмотров скрывал часть выдачи, смешивал разные поисковые запросы
в одном коротком цикле и мог повторно анализировать вакансию, по которой HH уже
зафиксировал отклик или потребовал действия кандидата.

## Решение

Запросы обходятся последовательно и циклически. Первая страница каждого запроса
определяет актуальную пагинацию, остальные страницы перемешиваются без повторов.
Ссылки одной страницы перемешиваются и делятся на сбалансированные группы с
настраиваемым максимальным размером. Один запуск активности обрабатывает одну
группу, после чего планировщик выдерживает полный интервал.

До анализа по ID проверяется таблица `vacancy_responses`. Терминальные статусы
`sent`, `already_sent`, `manual_required` и `unknown` запрещают повторный
анализ и отклик, но не запрещают открыть и прокрутить вакансию. Новая вакансия
просматривается при любой оценке; порог соответствия управляет только откликом.
Просмотры и оценки без попытки отклика больше не записываются.

Очередь обхода остаётся в памяти. После перезапуска она строится заново, а SQLite
защищает от повторных откликов. Автоподнятие работает по отдельному сроку в том же
кооперативном планировщике, потому что Playwright Sync API и постоянный профиль
Chromium нельзя безопасно разделять между потоками.

## Последствия

- вся доступная пагинация каждого запроса постепенно просматривается;
- новые объявления не теряются из-за прежней истории просмотров;
- перезапуск может повторить просмотр, но не терминальный отклик;
- одна группа ограничивает задержку проверки поднятия;
- старые параметры уникальности читаются для совместимости, но новый production-путь
  их не использует.
